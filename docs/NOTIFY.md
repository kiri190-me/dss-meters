# 교정 기한 알림 메일

교정 기한이 **다음 달**인 계측기를 매달 **1일**에 메일로 알린다.
기한이 닥쳐서 알리면 교정을 보낼 시간이 없기 때문이다.

예) 기한이 `2027-02` 인 계측기 → `2027-01-01` 에 발송

---

## 화면에서 하는 일

**관리자 머리말의 「알림 설정」** → http://localhost:3300/settings/notify

| | 내용 |
|---|---|
| 받는 사람 | 메일 주소·이름·**받을 언어**(한국어/日本語)를 등록한다. 잠시 끄고 켤 수 있다 |
| 메일 문구 | 제목 · 표 위에 오는 말 · 표 아래에 오는 말을 언어별로 고친다 |
| 수동 발송 | 1일에 나갔어야 했던 메일을 **지금 다시 보낸다** (아래 「손으로 다시 보내기」) |
| 발송 기록 | 언제 어느 기한을 몇 대·몇 명에게 보냈는지. 배치가 보낸 것과 손으로 보낸 것을 함께 보여 준다 |

### 문구의 자리표시자

문구 안에 두 개를 쓸 수 있다. 그 외는 그냥 글자로 나간다.

| | 바뀌는 값 |
|---|---|
| `{ym}` | 알리는 기한 (`2027-01`) |
| `{count}` | 계측기 대수 |

**계측기 표는 문구가 아니라 데이터라 자동으로 붙는다.** 화면에서 고치는 것은 말뿐이다.
입력하는 즉시 아래에 채워진 모습이 보이므로, 저장 전에 확인할 수 있다.

문구를 한 번도 저장하지 않았으면 코드의 기본 문구를 쓴다
(`src/lib/mail/template.ts`). 저장한 문구를 지우고 기본으로 되돌리려면
그 언어의 행을 지우면 된다.

---

## 누가 받는가

받는 사람으로 등록되고 **「받음」 상태인 사람**만 받는다. 한 명도 없으면 메일을 만들지 않는다.

받는 사람마다 언어가 따로다. 교산 담당자를 넣으면 그 사람만 일본어로 받는다.

## 무엇이 알림 대상인가

교정 기한이 그 달인 계측기 중, 아래 **네 상태는 빼고** 보낸다.

| 빼는 상태 | 왜 |
|---|---|
| 교정대상아님 | 더미로드 등 — 애초에 교정을 받지 않는다 |
| 고장(교정불가) | 고쳐서 쓸 수 없다 |
| 반납·발송 | 이미 교산으로 돌려보냈다 |
| 교정진행중 | 이미 교정 업체에 보냈다 — 또 알리면 잔소리가 된다 |

이 판단은 `src/lib/notify.ts` 의 `NOT_NOTIFIED` 한 곳에 있다.

## 매일 자동으로 돌아간다 (NAS · DSM 작업 스케줄러)

**이미 등록되어 있다.** 손댈 것이 없다.

> 🔴 2026-09-18 NAS 배포 전에는 이남준 님 PC 의 Windows 작업 스케줄러가 돌렸다.
> **지금은 NAS 다.** 개발 PC 를 꺼 두어도 알림은 나간다.

| 항목 | 값 |
|---|---|
| 작업 이름 | `DSS 교정 알림` (DSM → 제어판 → 작업 스케줄러, root 로 실행) |
| 실행 시각 | **매일 09:00** |
| 실행 내용 | `bash /volume1/dss/jobs/notify-daily.sh` (root 700) |
| 그 안에서 | `docker compose --profile tools run --rm tools-meters npm run send-notify` |

도커 명령을 스케줄러에 직접 적지 않고 스크립트를 거치는 이유는 **기록** 때문이다 —
1일이 아니라 그냥 끝난 날도 남겨야 "돌기는 했는지" 를 나중에 안다.
(스크립트와 설치 절차는 `dss-deploy` 의 `nas/jobs/notify-daily.sh` ·
`nas/setup/06-notify-install.sh` 에 있다. 이 저장소에는 없다.)

**매일 돌지만 실제로 나가는 것은 1일뿐이다.** 1일이 아니면 아무것도 하지 않고 끝난다.
날짜 판단을 스케줄러가 아니라 코드가 하는 이유는, 스케줄러 설정이 어딘가에서
조용히 바뀌어도 규칙은 코드에 남아 있게 하기 위해서다.

**같은 기한은 두 번 보내지 않는다.** `web_notifications` 에 성공 기록이 있으면 건너뛴다.

### 잘 돌고 있는지 보려면

DSM 의 작업 스케줄러 화면에서 마지막 실행 결과를 본다. 종료 코드 **0** 이면 성공이다.
로그를 직접 읽으려면 (NAS 에 SSH 로 붙어서):

```bash
ls -1t /volume1/dss/setup/logs/notify-*.log | head -3
cat "$(ls -1t /volume1/dss/setup/logs/notify-*.log | head -1)"
```

### 실행 로그

매번 `/volume1/dss/setup/logs/notify-날짜_시각.log` 에 쌓인다. 1일이 아니라 그냥
끝난 날도 남는다 — "돌기는 했는지" 를 나중에 알 수 있어야 하기 때문이다.
최근 **60개**(두 달치)만 남기고 오래된 것부터 지운다.

> 🔴 컨테이너 **안**의 `logs/notify.log` 는 보지 마라. 도구 컨테이너는 `--rm` 으로
> 잠깐 떴다 사라지고 그 자리에 볼륨이 붙어 있지 않아서, 그 파일은 실행이 끝나면
> 함께 사라진다. 실제로 남는 것은 위의 NAS 쪽 로그다.
> (개발 PC 에서 손으로 돌릴 때는 그대로 `logs/notify.log` 에 쌓인다.)

## 손으로 다시 보내기 (2026-11-18)

### 왜 있는가

2026-11-01 09:00 에 배치는 **정상으로 끝났다.** 로그는 「계측기 2대 · 받는 사람 3명 ·
3명에게 보냈습니다 · 정상 종료(0)」 였고 `web_notifications` 에도 `SENT` 로 적혔다.
**그런데 아무도 받지 못했다.** 보내는 주소(`SMTP_FROM`)의 도메인에 글자가 하나 더
붙어 있어서, 메일 서버는 로그인된 계정으로 받아 주고 받는 쪽은 없는 도메인에서 온
메일이라 조용히 버렸다. 설정은 고쳤지만, **「보냄으로 적혔는데 실제로는 못 받은」
상태가 실재한다**는 것이 남았다. 그래서 다시 보낼 길이 화면에 있다.

### 화면에서 (관리자만)

**「알림 설정」 → 맨 위 「교정 기한 알림」 카드 아래**

1. 지금 기준으로 **다음에 나갈 기한**과, 그 기한을 **언제 몇 명에게 보냈는지**가 적혀 있다.
2. `지금 다시 보내기` 를 누르면 **바로 나가지 않는다.** 무엇이 몇 명에게 나가는지
   적힌 확인 판이 펼쳐진다. 거기서 한 번 더 눌러야 나간다.
3. 보내는 동안 단추가 잠긴다 (메일 서버에 붙는 데 10초쯤 걸린다).
4. 끝나면 **몇 명에게 갔는지 · 실패했으면 까닭**이 그 자리에 뜬다.
5. 보낼 것이 없으면(계측기 0대 · 받는 사람 0명) 단추가 꺼져 있고 까닭이 옆에 적힌다.

보내는 대상은 화면에 적힌 그것 그대로다 — 안내 문구와 단추가 **같은 함수**로 기한과
대상을 고른다(`nextNotifyYm` · `listNotifyTargets` · `listActiveRecipients`).
**이미 보낸 기한이어도 보낸다.** 그것이 이 단추의 존재 이유다.

### 🔴 기록이 어디에 남는가

| | 어디에 |
|---|---|
| 배치(1일)가 보낸 것 | `web_notifications` 한 줄 + 감사 로그 `NOTIFY_SEND` |
| 손으로 다시 보낸 것 | **감사 로그 `NOTIFY_RESEND` 만** (누가·언제·어느 기한·몇 대·몇 명·실패 사유) |

수동 발송이 `web_notifications` 에 적지 않는 까닭: 그 표는 「이 기한은 보냈다」는
**자물쇠**이기도 해서 한 기한에 성공 기록이 하나뿐이도록 유니크 인덱스가 걸려 있다.
거기에 끼워 넣으려면 기존 행을 덮어쓰거나 결과를 거짓으로 적어야 하는데,
덮어쓰면 **처음 보낸 날이 사라진다** — 11-01 사고를 되짚은 근거가 바로 그 값이다.
사람이 한 일을 적는 자리는 원래 감사 로그다.
**발송 기록 표는 두 자리를 합쳐서 보여 주므로** 화면에서는 함께 보인다.

## 명령

```
npm run check-smtp                          메일 서버에 로그인만 해 본다 (안 보냄)
npm run preview-notify 2027-01              본문을 만들어 logs/ 에 저장한다 (안 보냄)
npm run send-notify                         매달 1일에만 실제로 나간다
npm run send-notify -- --dry                누구에게 무엇이 갈지만 본다 (안 보냄)
npm run send-notify -- --ym=2027-01 --force 그 기한을 지금 보낸다 (재발송)
```

### `--force` 는 이렇게 돈다 (2026-11-18 에 고쳤다)

`--force` 는 **두 가지 검사만** 건너뛴다 — 「오늘이 1일인가」와 「이미 보낸 기한인가」.
그 뒤는 평소와 같다. 그리고 기록은 이렇게 남는다:

| 그 기한에 성공 기록이 | 메일 | `web_notifications` | 감사 로그 | 종료 코드 |
|---|---|---|---|---|
| 없다 | 나간다 | **한 줄 들어간다** (평소와 똑같다) | `NOTIFY_SEND` | 0 |
| 이미 있다 | 나간다 | **그대로 둔다** (덮어쓰지 않는다) | `NOTIFY_SEND` | 0 |

기록을 그대로 둔 경우에는 로그에 그 사실이 적힌다:

```
  보냄  …
기록은 그대로 둡니다 — 2026-12 기한의 성공 기록이 이미 있습니다 (처음 보낸 날 2026-11-01, 3명).

=> 3명에게 보냈습니다.
```

> 🔴 **2026-11-18 전에는 아래쪽 줄에서 터졌다.** `--force` 가 중복 검사만 건너뛰고
> 기록 INSERT 는 그대로라, 이미 보낸 기한에 쓰면 **메일은 전부 나간 뒤** 유니크
> 위반으로 터져 **감사 로그도 못 남기고** 종료 코드 1 로 끝났다. 스케줄러는
> 「비정상 종료」로 표시하고 사람은 「안 나갔구나」로 읽었다 — 메일은 나갔는데.
> 11-01 사고의 정확한 거울이라 같은 날 함께 고쳤다.
> 🔵 중복 발송을 막는 것은 이 인덱스가 아니라 **보내기 전**의 `alreadySent` 검사다
> (메일은 기록보다 먼저 나간다). 그 검사는 그대로다 — 1일 배치는 지금도 두 번 보내지 않는다.

## 메일 서버 (cafe24)

값은 `.env.local` 에 있다. 웹메일의 **「환경설정 → POP3/SMTP 사용설정」** 화면에 적힌 그대로다.

| | 값 |
|---|---|
| SMTP_HOST | `smtp.cafe24.com` |
| SMTP_PORT | `587` |
| SMTP_USER | 메일 주소 전체 |

### 알아 둘 것

- **465 포트는 열려 있지 않다.** 587 로 붙어 STARTTLS 로 올린다.
- cafe24 서버가 **TLSv1 까지만** 하고 RFC 5746(안전한 재협상)을 지원하지 않는다.
  요즘 Node 는 이런 서버를 기본으로 거절하므로 `src/lib/mail/transport.ts` 에서
  예외를 열어 두었다. 사내에서 우리 메일 서버로만 나가는 연결이라 이 정도로 둔다.
- 웹메일 화면에서 **SMTP 연결이 '사용함'** 이어야 로그인이 된다.
- **비밀번호를 바꾸면 서버에 반영될 때까지 최대 30분쯤 걸린다.**
  바꾼 직후에는 `check-smtp` 가 535 로 실패하는 것이 정상이다.
- `smtp.cafe24.com` 은 서버 3대로 분산되어 있다. 반영 시점이 서버마다 다를 수 있다.

### 안 될 때

```
npm run check-smtp
```

`535` 가 뜨면 이 순서로 본다.

1. 웹메일에 그 비밀번호로 직접 로그인이 되는지
2. 환경설정 → POP3/SMTP 사용설정 에서 SMTP 연결이 '사용함' 인지
3. 비밀번호를 방금 바꿨다면 30분쯤 기다렸다가 다시

## 데이터

| 테이블 | 내용 |
|---|---|
| `web_notify_recipients` | 받는 사람. 소프트 삭제 4컬럼 |
| `web_notify_templates` | 언어별 문구 한 벌씩 |
| `web_notifications` | 배치의 발송 기록. `target_ym` 에 성공 기록은 하나만 (부분 유니크 인덱스) |

> 그 인덱스가 막는 것은 **기록**이 겹치는 것이다. 중복 **발송**을 막는 것은 보내기
> 전의 `alreadySent` 검사다 — 메일은 기록보다 먼저 나가기 때문에 순서가 그렇다.

수신자 추가·삭제, 문구 수정, 발송은 모두 감사 로그에 남는다
(`NOTIFY_RECIPIENT_*` · `NOTIFY_TEMPLATE_UPDATE` · `NOTIFY_SEND` · `NOTIFY_RESEND`).
